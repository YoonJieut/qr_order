# 사업자 클라이언트 앱 기능명세서

> 작성일: 2026-05-14

본 문서는 사업자용 client 앱의 1차 기능 범위와 화면별 동작 정책을 정의한다.
상세 스토리보드, API 요청/응답, DB 컬럼 매핑, 버튼별 활성화 정책은 후속 문서에서 보완한다.

## 1. 문서 범위

- 사업자용 client 앱의 메뉴 구조와 페이지별 주요 기능을 정의한다.
- 권한은 1차에서 메뉴 접근 권한 중심으로 정의한다.
- 등록, 수정, 비활성화, 재발급, 출력 등 액션별 세부 권한은 스토리보드 단계에서 보완한다.
- 업무 데이터는 원칙적으로 물리 삭제하지 않고 사용 여부 또는 상태값으로 비활성화한다.

## 2. 사용자 계정 및 권한 정책

### 2.1 계정 구분

#### client-admin

- 시스템 관리자(admin)가 서비스 구독 사업자에게 최초 부여하는 매장 대표 계정이다.
- client-admin은 해당 매장의 스태프 계정을 생성, 수정, 비활성화할 수 있다.
- client-admin은 스태프 계정별 메뉴 접근 권한을 부여하거나 삭제할 수 있다.
- client-admin은 `유저 정보 관리` 메뉴에 접근할 수 있다.

#### 스태프 계정

- client-admin이 생성하는 매장 내부 사용자 계정이다.
- 별도의 고정 권한 프리셋 또는 역할 프리셋은 제공하지 않는다.
- 스태프 계정의 접근 범위는 client-admin이 부여한 메뉴 접근 권한에 따른다.
- 스태프 계정은 `유저 정보 관리` 메뉴에 접근할 수 없다.
- 하나의 스태프 계정은 하나의 매장에만 소속된다.

### 2.2 권한 범위

- 1차 권한 관리는 메뉴 접근 권한을 기준으로 한다.
- 권한 프리셋은 제공하지 않는다.
- 메뉴 접근 권한이 있는 경우 해당 메뉴의 기본 조회, 등록, 수정, 비활성화 기능을 사용할 수 있다.
- 운영 영향이 큰 액션은 실행 전 ConfirmModal로 재확인한다.
- 버튼 단위 액션 권한은 기능명세서 단계에서 고정하지 않는다.
- 액션별 버튼 활성화/비활성화 정책은 상세 스토리보드 작성 단계에서 화면별로 정의한다.

### 2.3 유저 정보 관리 예외 정책

- `유저 정보 관리` 메뉴는 메뉴 권한 설정 대상에서 제외한다.
- client-admin이 실수로 필수 관리 메뉴 접근 권한을 제거하는 상황을 방지하기 위함이다.
- 해당 메뉴는 client-admin만 접근 가능하다.

## 3. 공통 데이터 삭제 정책

- client 앱의 업무 데이터는 원칙적으로 물리 삭제하지 않는다.
- 삭제성 동작은 사용 여부, 노출 여부, 상태값 변경 등 비활성화 방식으로 처리한다.
- 운영 이력, 주문 이력, 정산 데이터, 권한 변경 추적을 보존하기 위함이다.
- 화면 문구는 사용자가 이해하기 쉬운 표현을 우선하되, 실제 처리 방식은 비활성화로 정의한다.
- 비활성화된 데이터는 기본 목록에서 제외하거나 별도 필터로 조회할 수 있도록 추후 화면별로 정의한다.

## 4. 공통 알림 정책

- `window.alert`, `window.confirm`, `window.prompt`는 사용하지 않는다.
- 안내/성공 메시지는 AlertModal을 사용한다.
- 사용자 재확인이 필요한 작업은 ConfirmModal을 사용한다.
- 서버 또는 클라이언트 오류는 ErrorModal을 사용한다.
- 저장, 비활성화, QR 재발급, 주문 상태 변경처럼 운영 영향이 있는 액션은 ConfirmModal로 재확인한다.

## 6. 구현 우선순위 메모

- 정산 조회의 표 중심 집계를 먼저 구현하고, 메인 대시보드 차트는 같은 집계 기준이 확정된 뒤 구현한다.
- PG사 결제 승인(Mock Payment Adapter), 결제 취소, 환불, 부분 취소는 추후 검토 항목으로 둔다.
- 테이블 배치 GUI, 주문 보드 컬럼 크기 조정, 드래그 앤 드롭 상태 변경은 추후 편의 기능으로 둔다.

## 7. 현재 결정된 보완 정책

### 7.1 주문-결제-정산 1차 정책

- 1차 주문 취소는 결제 전/결제 후 주문 모두 허용한다.
- 현재 프로젝트 1차 범위에는 실제 PG 결제 승인/취소 연동이 없으므로, 주문 취소는 외부 PG 환불 처리가 아니라 DB 상태 변경으로 관리한다.
- 주문 취소 시 주문 상태를 `취소`로 변경한다.
- 결제 상태가 존재하는 주문의 경우 1차 기준으로 결제 상태도 `취소` 또는 이에 준하는 DB 상태로 변경한다.
- 정산 조회는 1차 기준으로 취소 상태의 주문/결제 데이터를 기준 삼아 취소 금액과 순매출을 계산한다.
- 실제 PG사 결제 승인(Mock Payment Adapter), 환불, 부분 취소 처리는 추후 검토한다.

### 7.2 권한 1차 정책

- 1차 권한 관리는 메뉴 접근 권한 중심으로 한다.
- 메뉴 접근 권한이 있는 사용자는 해당 메뉴의 기본 조작을 수행할 수 있다.
- 버튼 단위 액션 권한은 1차 기능명세서에서는 분리하지 않는다.
- 결제, 정산, QR 재발급, 매장 기본 정보 수정 등 민감 액션은 ConfirmModal로 재확인한다.
- 추후 필요 시 버튼 비활성화 및 역할/권한 조회를 통해 액션 권한을 확장한다.

### 7.3 비활성화 lifecycle 1차 정책

- 업무 데이터는 물리 삭제하지 않고 사용 여부 또는 상태값으로 비활성화한다.
- 활성 주문, 진행 중 주문, 고객 주문 화면 노출, QR 연결 등 운영 중 참조가 있는 데이터는 비활성화 전 ConfirmModal로 영향 범위를 안내한다.
- 진행 중 주문 처리에 직접 영향을 주는 경우 비활성화를 제한하거나 별도 정책을 적용한다.
- 정확한 제한 조건은 화면별 스토리보드와 API 정책에서 확정한다.

### 7.4 대시보드 1차 정책

- 메인 대시보드는 client 앱 로그인 후 기본 진입 화면으로 둔다.
- 1차 MVP 권장안은 차트 구현 전 KPI 카드 중심 대시보드를 먼저 제공하는 것이다.
- 차트는 정산 조회의 표 데이터 기준이 확정된 뒤 구현한다.

## 8. 스토리보드 단계에서 확정할 항목

- 화면별 버튼 활성화/비활성화 조건
- 등록/수정/비활성화/재발급/출력 버튼의 세부 권한 정책
- 각 화면의 loading, empty, validation error, access denied, retry 상태
- 주문 취소 가능 조건과 취소 확인 문구
- 결제 완료 주문의 취소 상태 처리 상세
- 실제 PG 환불 또는 부분 취소 처리 방식
- 정산 기준일: 주문일, 결제 승인일, 환불일, 영업일 마감 기준
- 비활성 데이터 조회 필터 제공 여부
- 활성 주문 또는 장바구니에서 참조 중인 테이블/메뉴/옵션 비활성화 제한 조건
- 문의사항 등록 화면을 모달로 할지 별도 페이지로 할지
- 메뉴 관리에서 옵션 관리로 이동하는 버튼 위치와 이동 방식
- 대시보드 차트 미구현 시 표시 방식
